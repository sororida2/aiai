Agent Loop 시스템 아키텍처 다이어그램 모음

OpenAI Agents SDK 기반 Agent Loop 프레임워크 — 전체 조감도 및 세부 구조 7종

1. 전체 시스템 조감도

사용자 요청이 오케스트레이터를 거쳐 Tool Registry, Prompt Store, 공통 하네스로 구성된 Agent Loop 시스템에 전달되고, Tool Registry는 어댑터를 통해 레거시 API/DB와 연결되는 구조

2. Tool 어댑터 내부 구조 (양면 어댑터)

오케스트레이터를 향한 의미론적 면(스키마, 설명)과 레거시 API를 향한 프로토콜적 면(호출, 인증, semantic 매핑) 두 개로 구성된 tool 어댑터 하나의 내부 구조

3. 오케스트레이터 내부 라우팅 흐름

사용자 요청이 Triage Agent에 도달해 Tool 스키마를 참조하여 판단한 뒤, 단일 tool을 직접 호출하거나 도메인별 Sub-Agent로 Handoff하고, 결과가 응답으로 조합되는 흐름

4. Prompt Store 계층 구조

공통 오케스트레이터 프롬프트, 도메인별 Tool 프롬프트, Few-shot 예시가 각각 독립적으로 관리되다가 런타임에 조합되어 모델 호출로 전달되는 구조

5. Guardrail 체인 순서

Tool 호출 요청이 Input Guardrail, Tool 실행, Output Guardrail을 순차로 거쳐 응답 반환에 이르며, 각 단계에서 실패 시 즉시 차단과 로그 기록으로 빠지는 흐름

6. Tracing Span 중첩 구조

하나의 요청 단위인 Trace 안에 오케스트레이터 판단 구간을 나타내는 Orchestrator Span이 있고, 그 안에 개별 tool 호출을 나타내는 두 개의 Tool Span이 중첩되어 기록되는 구조

7. Semantic 매핑 발굴 파이프라인

guardrail이 미확인 코드값을 발견해 조사 큐에 등록하면 데이터 분포 조사, UI 화면 역참조, 담당자 인터뷰 세 경로로 병행 조사하고, 결과가 confidence 태그와 함께 매핑 테이블에 갱신되어 어댑터에 반영되는 흐름

8. 현재 구현된 서비스 ↔ 프레임워크 연결도

지금 실제로 구현된 4개 서비스가 프레임워크의 어떤 조각(ToolRegistry·WorkflowRegistry·BaseAdapter·SemanticMapping·GuardrailChain)을 쓰는지, 그리고 서비스끼리 어떻게 연결되는지를 정리한 것. 점선은 코드로 직접 호출하는 관계, 라벨 붙은 점선은 프롬프트 문구로만 안내하고 코드 연결은 없는 관계

9. Orchestrator.handle() — 라우팅 + 인자 추출 흐름 (as-built)

choose_tool()로 tool을 고른 뒤, 호출자가 kwargs로 안 준 필드만 자연어에서 추측해 채우고(extract_arguments), 호출자가 준 값이 항상 우선하도록 병합한 다음 guardrail을 거쳐 tool을 실행하는 실제 구현 흐름

10. 동적 tool 연결 — Orchestrator._resolve_missing_via_other_tool() (as-built)

extract_arguments()로도 못 채운 필드가 남으면, 사람이 미리 고정해두지 않은 다른 tool을 찾아 불러서 그 결과를 요청에 반영해 다시 쓰고 처음부터 재시도한다 — 못 찾거나 실패하면 조용히 숨기지 않고 원래 흐름대로 정직하게 실패한다
