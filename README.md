# Agent Loop 시스템 아키텍처

OpenAI Agents SDK 기반으로 구축하는 Agent Loop 프레임워크 논의 정리. 청약진행상황 기능은 이 구조 위에 얹히는 첫 번째 사례일 뿐이며, 목적은 내년도 여러 AI 프로젝트의 참고모델이 될 범용 아키텍처를 세우는 것이다.

## 왜 이 구조가 필요한가

AI agent 기술(모델이 tool을 선택·호출하는 loop) 자체는 이미 SDK가 제공한다. 여기서 새로 만드는 건 기술이 아니라, 그 기술을 조직 차원에서 반복 사용 가능하게 만드는 **구조**다.

- 표준 프레임워크 없이 SDK를 그대로 쓰면, 프로젝트마다 아키텍처를 새로 설계하게 되어 유지보수 비용이 프로젝트 수에 비례해 발산한다.
- 여러 개발자가 동시에 다른 서비스를 붙일 때 충돌을 막으려면 registry/prompt 분리 구조가 필요하다.
- guardrail, tracing, 실패 처리 같은 운영 안전장치는 SDK가 훅만 제공할 뿐, 언제·어떻게 강제할지는 조직의 설계 몫이다.
- API가 늘어날 때마다 코드 재작성 없이 확장되려면(tool 추가 + 프롬프트 수정만으로), tool selection을 모델에 위임하는 구조 자체를 설계해야 한다.

표준화 대상은 각 API의 실제 폼(REST/gRPC, 인증 방식, 응답 스키마)이 아니라, agent가 보는 얇은 계약(이름·설명·입력 스키마·반환 형식) 뿐이다. 각 API는 그대로 두고, 그 위에 어댑터를 씌운다.

## 고객사가 요구한 5가지 과제

1. Agent Loop를 구조적으로 다룰 수 있는 프레임워크 및 베스트 프랙티스
2. 적절한 하네스의 베스트 프랙티스
3. Agent 내 신규 서비스 추가 시 병렬로 독립적 추가가 가능한 구조
4. 프롬프트의 분리 관리
5. 생성형의 내부 모듈화 사용 테스트 — API 단계별 호출 알고리즘 대신, API 추가 + 프롬프트 수정만으로 실시간 확장 가능하게 하는 접근

## 전체 구조

```
사용자 요청
  │
  ▼
Agent Loop 시스템
  ├── 오케스트레이터 (요청 라우팅)
  ├── Tool Registry (서비스 독립 등록)
  ├── Prompt Store (프롬프트 분리 관리)
  └── 공통 하네스 (Guardrail · Tracing · 재시도)
              │
              ▼ (Adapter)
         레거시 시스템 (API · DB)
```

### 오케스트레이터

Triage Agent가 Tool 스키마를 참조해 판단하고, 단일 tool을 직접 호출하거나 도메인별 Sub-Agent로 Handoff한다. 오케스트레이터는 tool의 내부 구현을 몰라도 되지만, tool의 스키마·설명에는 필연적으로 커플링된다 — 즉 인터페이스 수준에서만 커플링되고, 구현 수준에서는 커플링되지 않는 구조가 목표다. tool 설명이 모호하거나 서로 겹치면 라우팅 정확도가 떨어지므로, 신규 tool 추가 시 기존 tool과의 설명 중복을 점검하는 절차가 필요하다.

### Tool Registry — 양면 어댑터

새 서비스 추가 = 새 tool 파일 + 새 prompt 파일이며, 오케스트레이터 코드를 건드리지 않는 것이 목표다 — 구현체에서는 여기서 한 걸음 더 나가 `main.py`(조립 지점)조차 건드리지 않는다. 서비스 모듈은 `services/` 아래를 스캔하는 auto-discovery가 자동으로 찾아 등록하고, 등록 직후 참조 무결성(오탈자, 데코레이터 누락 등)까지 기동 시점에 검사한다. 자세한 구현은 `ARCHITECTURE.md`의 `registry/discovery.py` 절 참고. 각 tool 어댑터는 두 개의 이질적인 면을 가진다.

- **의미론적 면**: 스키마·설명·파라미터. 오케스트레이터가 유일하게 커플링되는 지점이며, 설계에 의해 결정되는 영역이다.
- **프로토콜적 면**: 실제 호출·인증·응답 정규화, 그리고 semantic 매핑 테이블. 레거시의 실제 스펙이라는 사실(fact)에 종속되는 영역이다.

두 면은 서로 독립적으로 변경 가능해야 하며, 이 격리가 어댑터가 존재하는 이유다.

### Prompt Store

프롬프트를 코드에서 분리해 계층으로 관리한다.

- 공통 오케스트레이터 프롬프트 (모든 요청에 적용)
- 도메인별 Tool 프롬프트 (tool별 독립 버전 관리 — Tool 어댑터의 의미론적 면과 직결)
- Few-shot 예시 (선택적 삽입)

런타임에 조합되어 모델 호출로 전달된다.

### 공통 하네스

모델/agent의 개별 실행을 감싸서 검증·관측·제어하는, 모델 자체와는 분리된 주변 인프라 계층. "관찰자"가 아니라 **개입 권한을 가진 계층**이다 — guardrail은 조건에 안 맞으면 그 자리에서 흐름을 중단시킨다.

- **Input Guardrail** → **Tool 실행** → **Output Guardrail** → **응답 반환** 순으로 체인이 걸리며, 어느 단계든 실패하면 즉시 차단 + 로그로 빠진다.
- **Tracing**: 하나의 요청(Trace) 안에 Orchestrator Span이 있고, 그 안에 개별 tool 호출들이 각자의 Tool Span으로 중첩 기록된다. Tool Span이 늘어나도 상위 구조는 그대로 유지된다.

**Tool-하네스 결합**: 하네스는 tool과 결합되지만 강결합은 아니다. 결합되는 건 하네스 엔진(guardrail 체인 실행기)이 아니라, tool이 자신의 출력 스키마·guardrail 규칙을 "선언"한 것을 하네스가 읽어서 실행하는 형태다. 오케스트레이터가 tool의 입력 스키마에 커플링되는 것과 같은 축의, 반대 방향 커플링이다. `@guardrail(output_schema=...)`처럼 규칙을 tool 옆에 선언해두면 느슨한 결합, 하네스 엔진 코드 안에 `if tool_name == "legacy_a": ...` 식 분기가 생기면 그게 진짜 강결합(안티패턴)이다.

## 레거시 통합 — semantic 매핑

레거시 API/DB는 문서화가 완벽하지 않은 경우가 대부분이라는 전제로 설계해야 한다.

- 코드값의 의미(예: 내부 상태코드 "99")는 어댑터가 아니라 사람이 최초 1회 조사해서 고정 자산으로 만들어야 한다. 자동화 대상이 아니다.
- 조사 경로: 실 데이터 분포 조사, 레거시 화면/리포트 역참조, 담당자 인터뷰.
- 매핑은 **confirmed / inferred**로 confidence를 구분해 관리하며, `inferred`는 판단 분기(승인/거부 등 중요 로직)에는 쓰지 않고 사람 검토용으로만 노출한다.
- 매핑에 없는 신규 코드값이 나오면 guardrail이 fail-fast로 차단하고 로그를 남기며, 이 로그가 조사 큐의 입구가 되는 지속적 발굴 파이프라인으로 이어진다.
- 어댑터는 프로토콜 변환기이면서 동시에 의미 정규화 계층이어야 한다 — 레거시의 지저분한 원시값을 그대로 모델에 노출하지 않는다.

## MCP 연동 시 고려사항

Claude connector 등이 쓰는 MCP(Model Context Protocol)는 지금까지 설계한 tool 어댑터 개념의 업계 표준화된 형태다. 채택 여부와 무관하게 알아둘 것.

- MCP가 표준화하는 건 tool 어댑터의 "의미론적 면"(name, description, input schema)과 통신 포맷(JSON-RPC 2.0, stdio 또는 HTTPS 기반 Streamable HTTP)이다. 프로토콜적 이질성(REST/SOAP/gRPC, 인증 방식 차이)은 흡수해주지만, 각 서비스 원시값의 의미(semantic)는 알지 못한다.
- MCP 2025-06-18부터 tool이 outputSchema(JSON Schema)를 선언하면 서버가 structuredContent로 그 스키마에 검증되는 응답을 반환하는 기능이 생겼다. 다만 이건 "형태(shape)" 검증이지 "의미(meaning)" 검증이 아니다 — `{"weather": "string"}`처럼 느슨하게 선언하면 원시 코드값("99")도 타입 조건은 만족해 그대로 통과한다. 열거형이 가능한 필드는 enum으로 강하게 제한해야 미확인 값을 스키마 단계에서 걸러낼 수 있다.
- 따라서 검증은 이중으로 짠다: ① tool 내부 정규화 로직(매핑 테이블로 원시값→정규화값 변환, 매핑 실패 시 정상 응답 대신 에러/미확인 처리) ② outputSchema의 enum/type 제약(1차 로직이 놓친 걸 잡는 구조적 backstop). 자유 텍스트·연속값 필드는 전부 enum화할 수 없으므로 타입/범위 제약까지만 걸고, 의미 해석이 필요하면 judged node로 넘긴다.
- MCP를 쓰든 자체 데코레이터 방식을 쓰든 semantic normalization(매핑 조사, confirmed/inferred 관리)은 프로토콜과 무관한 고정 비용이다. 프로토콜 선택은 "어댑터를 담는 그릇"만 정할 뿐, 안에 채워야 하는 도메인 지식 작업량은 줄여주지 않는다.
- 배포 토폴로지는 세 가지: 레거시 1개당 서버 1개(1:1), 여러 레거시를 게이트웨이 서버 하나가 aggregate(N:1), 혹은 애초에 MCP 없이 같은 프로세스 내 함수 호출(오케스트레이터·tool이 같은 OpenAI Agents SDK 서비스 안에 있을 때). 다른 애플리케이션/팀/외부 AI 클라이언트가 같은 어댑터를 재사용해야 할 때만 MCP 채택이 정당화된다. 지금 규모(단일 서비스, 레거시 소수)에서는 자체 데코레이터 방식이 더 가볍고, tool 스키마만 MCP와 유사하게 맞춰두면 향후 전환 비용을 낮출 수 있다.

## 근본적 한계 — 질문의 방법론은 사전에 결정된다

이 구조는 "AI가 무엇을 결정할 수 있는가의 범위를 넓히는 도구"가 아니라, **사람이 미리 정해둔 범위 안에서 AI가 그 결정을 얼마나 안전하게 대신하게 할 것인가를 다루는 도구**다. tool 카탈로그, judged/human_action의 선택지, guardrail 스키마, semantic 매핑 테이블 — 전부 코드 작성 시점에 사람이 닫아두는 자산이고, 자연어 요청이 실제로 착지할 수 있는 자리는 그 자산들뿐이다. 그래서 이 시스템은 "이미 있는 선택지 중 맞는 걸 고르는 것"(tool 라우팅)은 잘 하지만, "선택지 자체가 없는 곳에 새 선택지를 만들어내는 것"(예: 서로 다른 API가 같은 개념을 다르게 표현할 때 그 사이를 자동으로 잇는 것)은 원천적으로 못 한다 — 두 표현을 잇는 다리가 어딘가의 데이터 안에 이미 있어야만 그걸 찾아 쓸 수 있다.

이건 결함이 아니라 위 "레거시 통합" 절에서 이미 선택한 트레이드오프(감사 가능성을 위해 AI의 자유를 미리 좁혀둔다)의 다른 얼굴이다. 실제로 tool 선택 vs 인자 채우기를 나눠 실험해본 근거와 상세 논의는 `limitation.md` 참고.

**(업데이트) 인자 채우기도 이후 `AgentRunner.extract_arguments()`로 실제 동작하게 만들었다** — `orchestrator.handle("미국에 있는 대학 5개만 보여줘")`처럼 자연어만 던져도 라우팅+인자 채움이 끝까지 돈다. 다만 이건 위에서 말한 "다리가 없으면 못 잇는다"는 한계를 없앤 게 아니라, 그 다리가 없는 자리를 모델의 자유 생성으로 덮어버린 것뿐이다 — 결과가 맞는지 감사할 방법은 여전히 없다(`limitation.md`의 "업계 비교" 절에 상세).
